# virt-aa-helper-hook

A small workaround for libvirt's AppArmor integration on Ubuntu: it makes sure
that VMs using **libvirt storage volumes** (`<disk type='volume'>`) get
AppArmor rules for their actual disk files, so QEMU is not denied access to them.

## The problem

When AppArmor confinement is enabled, libvirt gives each VM its own AppArmor
profile (`/etc/apparmor.d/libvirt/libvirt-<uuid>`). The file access rules for
that profile live in `libvirt-<uuid>.files` and are generated by
`/usr/lib/libvirt/virt-aa-helper`. libvirtd calls this helper several times
over the VM's lifecycle, passing it the domain XML on stdin each time.

The helper can only grant access to file paths that appear in the XML it is
given. That breaks for disks that refer to a storage pool volume
(`<disk type='volume'>` with `<source pool='...' volume='...'/>`), because of the
order in which libvirt prepares a VM on start:

1. **The profile is created too early.** libvirt generates the VM's security
   label, which runs `virt-aa-helper -c`, *before* it resolves pool volumes to
   their actual files. At that point a volume disk has no file path in the XML,
   so the helper skips it. The `.files` file ends up with no rule for the disk
   image, and so none for its backing chain either.
2. **Later updates only add one path.** Right afterwards, libvirt resolves the
   volumes and keeps updating the profile as it prepares other resources (for
   example the VM's private directories under `/var/lib/libvirt/qemu`). It does
   this with `virt-aa-helper -r -F <path>`. These calls pass the now-complete
   XML, but with `-F` the helper only appends that one path and ignores the
   disks in the XML.
3. **Nothing goes back for the disks.** During a normal start, nothing makes
   the helper regenerate the full rule set from the resolved XML. QEMU is then
   denied access to the volume's image file (AppArmor `DENIED` in the kernel
   log) and the VM fails to start.

Disks that point directly at a file or block device (`type='file'` /
`type='block'`) are not affected, because their paths are already in the XML
when the profile is created.

## How it works

The package puts a wrapper around `virt-aa-helper` without changing
libvirt itself:

1. **Intercepting the helper call.** A systemd drop-in for `libvirtd.service`
   sets `LD_PRELOAD` to a tiny shared library (`virt-aa-helper-hook.so`). The
   library wraps `execve()`, so when libvirtd runs
   `/usr/lib/libvirt/virt-aa-helper`, the hook script
   `/usr/lib/libvirt/virt-aa-helper-hook` runs in its place.

2. **Running the original helper.** The hook script passes the same
   arguments and domain XML to the real helper, through a symlink
   (`virt-aa-helper-unhooked`) that the preload library does not redirect.
   Everything libvirt normally does still happens unchanged.

3. **Adding the missing rules.** When the call creates or updates a profile
   (`-c` / `-r`, not a dry run), the hook runs the real helper a second time in
   dry-run mode on the same XML, without `-F`. That makes the helper generate
   the full rule set from the XML it was just given. By the time of the `-r -F`
   calls described above, the XML includes the resolved volume paths, and the
   helper detects the backing chain itself. Any rules that are not yet in the
   VM's `.files` file are appended to it.

The hook doesn't reload the AppArmor profile itself. The appended rules take
effect the next time libvirt has `virt-aa-helper` reload the profile. During
start-up this happens straight away, because libvirt updates the profile
several times in a row before QEMU is launched.

The hook only ever adds rules that `virt-aa-helper` itself generates from the
domain XML. It doesn't grant more than libvirt would if the volumes had been
resolved before the profile was created.

The hook script runs under its own AppArmor profile
(`usr.lib.libvirt.virt-aa-helper-hook`). That profile only lets it run a shell
and a few coreutils, hand off to the real `virt-aa-helper` (which keeps its own
profile), and append to the per-VM `libvirt-<uuid>.files` files. The preload
library also removes itself from `LD_PRELOAD` once loaded, so processes started
by libvirtd, such as QEMU, don't inherit it.

## Installation

Prebuilt `.deb` packages are attached to the
[GitHub releases](https://github.com/dasch-swiss/virt-aa-helper-hook/releases).

```sh
sudo apt install ./virt-aa-helper-hook_<version>_amd64.deb
sudo systemctl restart libvirtd
```

The package loads its AppArmor profile and reloads systemd on install. You
still have to **restart libvirtd yourself** so the `LD_PRELOAD` drop-in takes
effect. Running VMs keep their current profiles. The hook applies the next time
a VM's profile is created or updated, for example when the VM is started.

### Uninstalling

```sh
sudo apt remove virt-aa-helper-hook
sudo systemctl restart libvirtd
```

## Compatibility

- Built for Ubuntu 24.04 (noble) and Ubuntu 26.04 (resolute). The AppArmor
  profile also covers the Rust coreutils (uutils) paths used in 26.04.
- The hook is loaded via `LD_PRELOAD` set in a systemd drop-in. If another
  drop-in or `/etc/default/libvirtd` also sets `LD_PRELOAD`, it replaces the
  hook's value and the hook is not loaded.
- Only the monolithic `libvirtd` daemon is hooked. It has no effect on
  libvirt's modular daemons (`virtqemud`, ...).

## Building from source

Build dependencies (Debian/Ubuntu):

```sh
sudo apt install gcc build-essential devscripts debhelper dh-apparmor
```

Build the package:

```sh
make package
```

The resulting `.deb` and source package files are written to `build/`.

### Releasing

1. Bump `VERSION` in `virt-aa-helper-hook/Makefile`.
2. `make changelog-update` adds a new `<VERSION>-1` entry to
   `debian/changelog` and opens an editor to write the release notes.
3. `make changelog-release` finalizes the entry by setting the distribution
   and the timestamp. Check the distribution and change it by hand if needed.
4. Commit, merge to `main`, and push a tag `v<VERSION>`. CI builds the package
   and creates a GitHub release with it attached. The tag must match `VERSION`.

CI also runs `make package` on every push to `main`.
